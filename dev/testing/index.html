Testing and CI¶

How the driver is checked: host tests against a model of the chip, a fuzzer that corrupts what the chip sends back, compiled documentation, an install test, ESP32 and Cortex-M builds, static analysis and measured quality gates, on every pull request.

Host tests¶

The tests build the real driver against a protocol and register model of the TLE92466ED: 32-bit frames with the CRC it checks while CRC_EN is set, the reply one frame later in the 16-bit, 22-bit or critical fault format, the reset values, Config and Mission Mode with their rules, clear-on-write flags with the two clears OC and OTP_ECC_ERR need, a channel kept off while it has a fault, parallel pairs, INIT_DONE, the SPI watchdog, the feedback freeze with a measurement period from the dither clock, and the self-test. The mock bus adds the faults a real line shows: a failed transfer, MISO stuck low or high, MOSI looped back, a bit flipped on MISO or MOSI, a frame the chip ignores or never sees, a reply replaced by any word. They build with the firmware's flags, -fno-exceptions -fno-rtti, and warnings as errors, on GCC and Clang.

cmake -S . -B build -DTLE92466ED_BUILD_TESTS=ON
cmake --build build
ctest --test-dir build --output-on-failure

The model stands alone¶

tests/mock_tle92466ed.hpp is written from the datasheet, not from the driver: it does not include tle92466ed_registers.hpp or tle92466ed_types.hpp. Its register map, field masks, reset values, timing and CRC-8 are its own (namespace tle92466ed_test::chip, each with the datasheet section), so a wrong constant in the driver cannot hide behind the same wrong constant in the model (handbook KB-TST-030). tests/test_model.cpp compares the two at compile time:

When the build stops on one of these, one of the two maps is wrong: check it against the section the model names, and fix that one. A new register goes into both, with its check. Every behaviour found on hardware becomes a fault mode of the model and a test that fails on the code before the fix; a chip with timing gets a virtual clock in the model (here Elapse(), driven by the mock port's DelayUs()).

The model's limits¶

The model is written from the datasheet, so it shares the driver's reading of the datasheet wherever the datasheet leaves room. These shared assumptions are not proven by the tests; each has a bench step in Status and limitations:

  • A 1 clears an rwh flag and a 0 leaves it; an rw flag takes the value written; OC and OTP_ECC_ERR need two clears.
  • CH_CTRL, MODE, CH_CONFIG and SETPOINT read back what was written; a slave reads MODE and SETPOINT as 0.
  • The reply to a write carries the register after the write. Section 5.2.1 allows the contents before it too, so the knob write_reply_before_write gives that reading and tle92466ed_host_tests_reply_before_write runs every host test under it (the build defines TLE92466ED_MODEL_REPLY_BEFORE_WRITE); the driver must pass both.
  • CHIPID0..2 and every register from FB_STAT on answer with 22-bit replies.
  • A frame the chip ignores leaves the previous reply to be sent again; the first reply after a reset is all zeros.
  • The don't-care bits of a read frame are ignored; replies always carry a CRC.
  • INIT_DONE after a reset or a clock change takes init_delay_us (50 µs), the self-test 500 µs: the datasheet gives neither.
  • The feedback is synthetic (the setpoint, or load_ua, over one dither period); the frame time is 32 SCK periods plus 1 µs at 4 MHz.
  • An OC in a pair disables both channels; COTERR switches every stage off and keeps Mission Mode; VPRE_OV switches them off; COTWARN and VBAT faults are reported only; a channel OTW or OTE blocks Mission Mode entry.

The hardware lessons, as tests¶

Each rule the handbook took from testing drivers on real hardware has a code path and a model test:

Fuzz tests¶

Everything the driver reads comes from the chip over the bus, so the data read is what a noisy cable, a wrong part or a broken chip controls. tests/fuzz/fuzz_tle92466ed.cpp lets libFuzzer choose a configuration, then up to 1024 driver calls, and on every bus transfer what the bus does: pass it to the model, fail it, flip bits of the reply or replace it. Between calls it can change the chip: another version, an unprogrammed OTP, INIT_DONE that never comes, events that cannot be cleared, supply, clock, channel and data faults, the Critical Fault state, a refused Mission Mode, time passing, a brown-out. After every call it checks the driver's promises and aborts, naming the line, when one breaks:

  • a failed call returns an Error the enum defines and T{};
  • before EnsureInitialized() no call makes a transfer; InvalidArgument and WrongState mean nothing was sent;
  • UnexpectedReset leaves the driver uninitialised;
  • a programmed setpoint is inside the operating range and is what GetCurrentSetpoint() reports;
  • feedback is a duty of at most 100 % over a measurement period;
  • every transfer is one 32-bit frame with both buffers, and every log line is a non-empty plain-text message.
# libFuzzer needs Clang (on macOS, Homebrew's LLVM)
cmake -S . -B build-fuzz -DCMAKE_CXX_COMPILER=clang++ -DTLE92466ED_BUILD_TESTS=ON -DTLE92466ED_BUILD_FUZZERS=ON
cmake --build build-fuzz --target fuzz_tle92466ed
./build-fuzz/tests/fuzz/fuzz_tle92466ed -max_total_time=120 tests/fuzz/corpus/fuzz_tle92466ed

The same file also builds without libFuzzer as fuzz_replay_fuzz_tle92466ed, and CTest replays every input in tests/fuzz/corpus/fuzz_tle92466ed/ on GCC and Clang (tle92466ed_fuzz_tle92466ed_corpus): the seeds, and every input that ever broke a promise (name it regress-*), so a fixed bug stays fixed. CI fuzzes for 120 s on every pull request, from the seeds plus a corpus it keeps between runs (job Host quality / fuzz).

Quality gates¶

The Host quality job measures the library code, inc/ and src/ only (tests and examples are left out), and fails when a value is over the limits of this repository's assurance level, high (set in .kokeb/handbook.yml, defined by the handbook's ADR-0020):

Gate Tool and how it is measured Limit at high
Complexity lizard 1.24.1, modified cyclomatic complexity (-m: a switch counts once) per function CCN at most 15
Function length lizard, lines of code per function at most 60
Parameters lizard, per function at most 6
Line coverage GCC 14 --coverage -O0, every CTest, gcovr 8.7 --merge-lines (a template's lines count once across its instances), --exclude-unreachable-branches --exclude-throw-branches at least 85 %
Branch coverage same run at least 75 %
MC/DC GCC -fcondition-coverage, same run measured, not gated at high (100 % at safety)
Sanitizers Clang, -fsanitize=address,undefined -fno-sanitize-recover=all, every CTest no report
Fuzzing libFuzzer with ASan and UBSan, 120 s per target no broken promise

The reports are in the run's host-quality-reports artifact and its step summary. To run the gates locally:

# Coverage (GCC 14 or later), then the complexity limits
cmake -S . -B build-cov -DCMAKE_CXX_COMPILER=g++-14 -DTLE92466ED_BUILD_TESTS=ON \
  -DCMAKE_CXX_FLAGS="--coverage -O0 -fcondition-coverage"
cmake --build build-cov && ctest --test-dir build-cov
gcovr --root . --filter inc/ --filter src/ --merge-lines --exclude-unreachable-branches --txt build-cov
lizard -m -C 15 -L 60 -a 6 inc src

# Sanitizers (Clang)
cmake -S . -B build-san -DCMAKE_CXX_COMPILER=clang++ -DTLE92466ED_BUILD_TESTS=ON \
  -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all -O1 -g"
cmake --build build-san && ctest --test-dir build-san --output-on-failure

The fuzz gate runs locally as shown in Fuzz tests.

clang-tidy 20 (_config/.clang-tidy: bugprone, CERT, clang-analyzer, cppcoreguidelines, modernize, performance, portability and readability, each disabled check with its reason) and cppcheck (strict) run in the C++ lint and Repository checks jobs and fail on any finding.

The MISRA job (ci-misra.yml) runs the shared ru-misra workflow of ci-tools at level high: it traces a host build and the Cortex-M build (tle92466ed_optimised_build) of every translation unit, checks them against MISRA C++:2023 and the handbook's C++20 profile (the CodeQL coding-standards and profile packs, plus the validated clang-tidy and cppcheck checks), and reports each finding against the handbook's compliance matrix and deviation records. A finding is fixed in the code; a deliberate exception names its deviation on the line before it (// codeql::misra_deviation_next_line(MD-CPP-009) above the .ipp include of inc/tle92466ed.hpp). Until the repository is public the job runs with open_source_prerelease: true, the declaration that the code is released under the licence in LICENSE and is to be published.

Documentation snippets¶

Every C++ block on this site is included from tests/docs/, which the host build compiles (target tle92466ed_doc_snippets) with the driver instantiated over the documented port. A change to the API that breaks a page breaks the build first. The README's example is a generated copy of the same file; kokeb-docs check fails when it drifts.

CI workflows¶

Everything runs from ci.yml, which calls one workflow file per check and ends in the CI gate job, the single required check (CI gate / gate).

Job What it checks
Host tests GCC, then Clang (one job), build and run every test above, then build and run examples/host on its own
Host quality The gates above: complexity, coverage, sanitizers, fuzzing
Cross-compile arm-none-eabi-g++ for Cortex-M0+, M4F and M7F with the strict flags, warnings as errors (nothing linked)
C++ lint clang-format and clang-tidy over the sources
MISRA MISRA C++:2023 and the C++20 profile on traced host and Cortex-M builds, at level high (see Quality gates)
Docs Strict site build (_config/mkdocs.yml), figure and generated-region drift, Doxygen (_config/Doxyfile), offline link check, Lighthouse
Repository checks One job: DCO on pull requests, the org standard, Markdown and YAML lint, the Kokeb Labs handbook rules for .kokeb/handbook.yml (by rule ID), template drift (warns only) and cppcheck over the driver sources; a second job runs the handbook's source checks (include guards, bus requirements, raw access)
CI gate Passes only if every job above passed: the one required check

The ESP32 examples job builds every app in examples/esp32/app_config.yml, for each listed ESP-IDF version and build type, with the repository root as the driver's component, and lints the example sources. The gate needs it too.

The workflows call the shared, versioned workflows of kokeb-labs/ci-tools at @v1.

On hardware¶

The ESP32 example (Examples) is the bench test: it drives LOAD0 at 300 mA and logs its feedback and any fault twice a second. The bench steps, and what each confirms, are in Status and limitations. Record the board and the result in the pull request's bench-status section.
